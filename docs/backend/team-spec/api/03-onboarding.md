# 온보딩 API

닉네임과 두더지, 관심사, 자기소개 질문과 답변을 정하고 땅굴을 만드는 온보딩을 다룬다. 규칙은 [API 공통 규칙](../api-convention.md)을 따른다.

- 명세: [03 온보딩](../spec/03-onboarding.md)
- DB 설계: [계정 · 프로필 · 관심사 · 질문](../db/account.md), [들판 · 땅굴](../db/burrow.md)

## 목록

"온보딩 중에도"는 온보딩을 마치지 않은 계정도 부를 수 있다는 뜻이다([로그인 · 회원가입 API](02-auth.md#온보딩을-마치지-않은-계정)).

| 메서드 | 주소 | 하는 일 | 로그인 | 명세의 화면 · 항목 |
|---|---|---|---|---|
| `POST` | `/api/v1/nicknames/check` | 닉네임을 쓸 수 있는지 확인하고 5분 동안 맡아 둔다 | 필요(온보딩 중에도) | 온보딩 1 · 2, 04 내 정보 수정 1 |
| `POST` | `/api/v1/me/onboarding/complete` | 온보딩에서 정한 값을 한 번에 저장하고 땅굴을 만든다 | 필요(온보딩 중에도) | 온보딩 4 · 5 |

온보딩만 쓰는 API는 이 둘이다. 관심사 목록과 질문 목록은 [공통 API](00-common.md)를 쓴다.

## 화면마다 부르는 API

| 화면 | 부르는 때 | API | API 없이 프론트엔드가 하는 것 |
|---|---|---|---|
| 온보딩 1 – 나를 부르는 이름 | "다음" | `POST /api/v1/nicknames/check` | 두더지 아이템 목록과 그림, 랜덤으로 꾸미기, 미리보기 |
| 온보딩 2 – 관심 분야 고르기 | 화면을 열 때 | [`GET /api/v1/interest-categories`](00-common.md#get-apiv1interest-categories) | 대분류의 아이콘, 지금 보는 대분류, 대분류마다 고른 개수 배지, 고른 관심사와 순서, 3 ~ 10개 제한 |
| 온보딩 3 – 자기소개 | 화면을 열 때 | [`GET /api/v1/intro-questions`](00-common.md#get-apiv1intro-questions) | 추천 · 관심사 · TMI 필터, 고른 질문과 답변, 글자 수, 미리보기 |
| 온보딩 3a – 땅굴 만드는 중 | 부르지 않는다 | | 진행 체크리스트, 땅굴 무드, 가구 매칭 목록 |
| 온보딩 4 – 땅굴 미리보기 | "관심사 확정" | `POST /api/v1/me/onboarding/complete` | 땅굴 미리보기, 땅굴 정보 카드 |

온보딩 4의 땅굴 정보 카드는 캠퍼스 · 기수 · 층도 보여 준다. 이 셋은 화면에서 고른 값이 아니라 SSAFY 인증 때 서버에 저장한 값이라, [`GET /api/v1/me`](02-auth.md#get-apiv1me)가 주는 `campusName`, `generation`, `floor`로 그린다.

## 영역 규칙

### 저장하는 때

온보딩 1 ~ 4에서 정한 값은 온보딩 4의 "관심사 확정"을 누르기 전까지 DB에 저장하지 않는다. 프론트엔드가 화면 상태로 갖고 있다가 확정 API 한 번에 모두 보낸다([DB 설계](../db/account.md)의 A4). 닉네임만은 확인할 때 임시 저장소에 5분 동안 맡아 둔다([닉네임 맡아 두기](#닉네임-맡아-두기)).

| 명세의 규칙 | API에서는 |
|---|---|
| 도중에 나가면 고른 내용이 저장되지 않는다 | 확정 전에는 DB에 남는 것이 없다. 맡아 둔 닉네임은 5분 뒤 풀린다. 다음에 로그인하면 `nextStep`이 `ONBOARDING`이라 온보딩 1부터 빈 상태로 시작한다 |
| 이전 단계로 돌아가도 고른 값이 남는다 | 프론트엔드의 화면 상태다. API를 부르지 않는다 |
| "관심사 재선택"으로 다시 고르면 땅굴을 새로 만든다 | 미리보기를 프론트엔드가 다시 그릴 뿐이다. 서버의 땅굴은 확정할 때 한 번만 만든다 |

### 닉네임 맡아 두기

닉네임을 확인한 뒤 확정하기 전에 다른 사람이 같은 닉네임을 가져가는 일을 줄이려고, 확인에 성공한 닉네임을 그 계정 몫으로 잠깐 맡아 둔다.

- 맡아 두는 시간은 확인한 때부터 5분이다. 맡아 둔 기록은 DB가 아니라 임시 저장소(Redis)에 두고, 5분이 지나면 저절로 사라진다.
- 맡아 둔 동안 다른 계정이 같은 닉네임을 확인하거나 저장하려 하면 `NICKNAME_DUPLICATED`로 답한다.
- 한 계정은 닉네임을 하나만 맡는다. 다른 닉네임을 확인하면 앞의 것은 풀린다.
- 같은 계정이 같은 닉네임을 다시 확인하면 5분을 새로 센다.
- 5분이 지나 풀린 뒤에도, 그 사이 같은 닉네임을 쓰기 시작한 사람이 없으면 확정 API는 그대로 저장한다. 다른 사람이 쓰기 시작했으면 `NICKNAME_DUPLICATED`로 답한다.
- 닉네임을 저장하면(온보딩 확정, 내 정보 수정) 그 계정이 맡아 둔 기록을 지운다.

두 사람이 같은 닉네임을 갖는 일은 맡아 두기와 상관없이 `user_profile.nickname`의 UNIQUE가 막는다. 맡아 두기는 늦은 사람이 확정 단계에서야 알게 되는 일을 줄이는 장치다.

### 닉네임 규칙

닉네임 확인과 온보딩 확정이 같은 규칙을 쓴다(KAN-44).

- 앞뒤 공백은 지우고 본다. `"  두더지왕  "`은 `"두더지왕"`이다.
- 한글(완성된 글자), 영어, 숫자로 1 ~ 12자다. 가운데 공백, 특수문자, 이모지, 낱자(`ㅋㅋ`)는 `400`과 `INVALID_INPUT`이다. 이때 `fields`의 `message`는 "한글, 영어, 숫자로 1 ~ 12자여야 합니다."다.
- 영어 대소문자만 다른 닉네임은 같은 닉네임으로 본다. `Mole`을 누가 쓰고 있으면 `mole`은 `NICKNAME_DUPLICATED`다. DB의 정렬 규칙(`utf8mb4_0900_ai_ci`)이 UNIQUE를 이렇게 비교하므로 맡아 두기도 같게 맞췄다.
- 닉네임 확인은 몇 번을 불러도 제한하지 않는다.

### 추천 질문

온보딩 3의 "추천" 필터는 서버가 따로 주지 않는다. 고른 관심사가 아직 서버에 없기 때문이다. 프론트엔드가 [`GET /api/v1/intro-questions`](00-common.md#get-apiv1intro-questions)의 목록과 온보딩 2에서 고른 관심사로 고른다.

1. 내가 고른 관심사의 대분류에 딸린 관심사 질문 2개. `type`이 `INTEREST`이고 `interestCategoryId`가 내 관심사의 `interestCategoryId` 가운데 하나인 질문이다.
2. TMI 질문 1개. `type`이 `TMI`인 질문이다.
3. 1의 질문이 2개보다 적으면 TMI 질문으로 채워 모두 3개를 만든다.

"관심사" 필터와 "TMI" 필터도 같은 목록을 `type`으로 나눠 보여 준다.

### 두더지 아이템

두더지 아이템의 목록과 그림은 프론트엔드가 갖는다([DB 설계](../db/README.md)의 G4). 서버로는 부위마다 고른 아이템의 코드만 보낸다.

- 코드는 영어 대문자, 숫자, 밑줄로 쓰고 30자를 넘지 않는다(`CAP_RED`).
- "없음"을 고른 부위는 `null`을 보낸다.
- 서버는 코드의 모양만 검사한다. 프론트엔드의 아이템 목록에 있는 코드인지는 검사하지 않는다.
- 프론트엔드는 모르는 아이템 코드를 "없음"으로 그린다. 화면을 거치지 않고 보낸 코드나, 나중에 목록에서 뺀 아이템의 코드가 DB에 남아 있을 수 있다.

### 가구와 땅굴 무드

가구는 세부 관심사마다 하나로 정해져 있고, 어느 관심사에 어느 가구인지와 그 그림은 프론트엔드가 갖는다. 땅굴 무드는 대표 관심사(고른 순서에서 맨 앞)의 대분류로 프론트엔드가 정한다. 서버는 가구와 무드를 저장하지도 주지도 않는다.

그래서 온보딩 3a의 무드와 가구 매칭 목록, 온보딩 4의 땅굴 미리보기는 API 없이 고른 관심사만으로 그린다. "관심사 가구 N개"의 N은 고른 관심사의 개수다.

## POST /api/v1/nicknames/check

닉네임을 쓸 수 있는지 확인하고, 쓸 수 있으면 요청한 계정 몫으로 5분 동안 맡아 둔다. 온보딩 1의 "다음"을 누를 때 부르고, 내 정보 수정에서 닉네임을 바꿀 때도 쓴다. DB에는 아무것도 저장하지 않는다.

- 로그인: 필요(온보딩 중에도)
- 명세: 온보딩 1 · 2, 04 내 정보 수정 1

### 요청

| 위치 | 이름 | 타입 | 필수 | 설명 |
|---|---|---|---|---|
| 본문 | `nickname` | 문자열 | ✓ | 확인할 닉네임. 앞뒤 공백을 지운 뒤 한글 · 영어 · 숫자로 1 ~ 12자([닉네임 규칙](#닉네임-규칙)) |

```text
POST /api/v1/nicknames/check
```

```json
{ "nickname": "두더지왕" }
```

### 서버가 하는 일

1. `nickname`의 앞뒤 공백을 지우고 [닉네임 규칙](#닉네임-규칙)에 맞는지 본다. 아니면 `400`과 `INVALID_INPUT`.
2. `user_profile.nickname`에 같은 닉네임이 있는지 본다. 영어 대소문자만 다른 닉네임도 같은 것으로 본다. 요청한 사람 자신의 닉네임은 뺀다(내 정보 수정에서 지금 닉네임을 그대로 둘 때). 있으면 `409`와 `NICKNAME_DUPLICATED`.
3. 다른 계정이 그 닉네임을 맡아 두었는지 본다. 맡아 둔 시간이 남아 있으면 `409`와 `NICKNAME_DUPLICATED`.
4. 이 계정이 맡아 둔 다른 닉네임이 있으면 푼다.
5. 그 닉네임을 이 계정 몫으로 5분 동안 맡아 둔다. 이미 이 계정이 맡아 둔 닉네임이면 5분을 새로 센다.

| 값 | 저장하는 곳 |
|---|---|
| 맡아 둔 닉네임, 맡은 계정 | 임시 저장소(Redis). 5분 뒤 저절로 사라진다 |

맡아 두는 규칙은 [닉네임 맡아 두기](#닉네임-맡아-두기)에 있다.

### 응답 `data`

성공이면 `200`이다. 쓸 수 있는 닉네임이고, 지금부터 5분 동안 이 계정 몫이다.

| 이름 | 타입 | 설명 | 값이 오는 곳 |
|---|---|---|---|
| `expiresAt` | 시각 | 맡아 둔 것이 풀리는 시각 | 임시 저장소: 확인한 시각에 5분을 더한 값 |

### 응답 예시

쓸 수 있을 때:

```json
{
  "success": true,
  "data": { "expiresAt": "2026-11-20T03:05:00Z" },
  "error": null
}
```

다른 사람이 쓰고 있거나 맡아 두었을 때:

```json
{
  "success": false,
  "data": null,
  "error": {
    "code": "NICKNAME_DUPLICATED",
    "message": "이미 사용 중인 닉네임입니다.",
    "fields": null,
    "detail": null
  }
}
```

### 에러

| 상태 | `code` | 때 |
|---|---|---|
| `409` | `NICKNAME_DUPLICATED` | 다른 사람이 쓰고 있거나 맡아 둔 닉네임 |

## POST /api/v1/me/onboarding/complete

온보딩에서 정한 닉네임, 두더지, 관심사, 질문과 답변을 한 번에 저장하고 땅굴을 만든다. 온보딩 4의 "관심사 확정"을 누를 때 부른다. 성공하면 가입이 모두 끝나 `nextStep`이 `HOME`이 된다.

- 로그인: 필요(온보딩 중에도)
- 명세: 온보딩 4 · 5, 영역 규칙 "정하는 값의 조건"

### 요청

| 위치 | 이름 | 타입 | 필수 | 설명 |
|---|---|---|---|---|
| 본문 | `nickname` | 문자열 | ✓ | 닉네임. 앞뒤 공백을 지운 뒤 한글 · 영어 · 숫자로 1 ~ 12자([닉네임 규칙](#닉네임-규칙)) |
| 본문 | `mole` | 객체 | ✓ | 두더지 아이템. 네 부위를 모두 보낸다 |
| 본문 | `mole.head` | 문자열 | ✓ | 머리 아이템 코드. "없음"이면 `null` |
| 본문 | `mole.face` | 문자열 | ✓ | 얼굴 아이템 코드. "없음"이면 `null` |
| 본문 | `mole.neck` | 문자열 | ✓ | 목 아이템 코드. "없음"이면 `null` |
| 본문 | `mole.hand` | 문자열 | ✓ | 손 아이템 코드. "없음"이면 `null` |
| 본문 | `interestIds` | 목록 | ✓ | 고른 세부 관심사의 id. 3 ~ 10개이고 같은 id를 두 번 넣지 않는다. 고른 순서대로 보낸다. 첫 번째가 대표 관심사다 |
| 본문 | `answers` | 목록 | ✓ | 고른 질문과 답변. 정확히 3개다. 보낸 순서가 자기소개에서 보이는 순서다 |
| 본문 | `answers[].introQuestionId` | 숫자 | ✓ | 질문의 id. 세 질문이 서로 달라야 한다 |
| 본문 | `answers[].answer` | 문자열 | ✓ | 답변. 10 ~ 50자. 이모지도 한 자로 센다(DB의 `CHAR_LENGTH`와 같은 기준) |

```text
POST /api/v1/me/onboarding/complete
```

```json
{
  "nickname": "두더지왕",
  "mole": { "head": "CAP_RED", "face": null, "neck": "SCARF_GREEN", "hand": null },
  "interestIds": [12, 47, 5],
  "answers": [
    { "introQuestionId": 5, "answer": "운동하고 나면 무조건 제로 콜라를 마셔요" },
    { "introQuestionId": 2, "answer": "요즘은 인디 밴드 노래만 돌려 듣고 있어요" },
    { "introQuestionId": 21, "answer": "출퇴근용으로 산 접이식 자전거가 최고예요" }
  ]
}
```

### 서버가 하는 일

1. 이미 온보딩을 마친 계정이면(`user.onboarded_at`이 있음) 아무것도 바꾸지 않고, 요청 본문도 보지 않고, 지금의 값으로 `200`으로 답한다. 같은 요청이 두 번 와도 땅굴이 둘 생기지 않는다.
2. 입력값의 모양을 본다. [닉네임 규칙](#닉네임-규칙), 아이템 코드의 모양, 관심사 개수와 겹침, 답변 개수, 질문 겹침, 답변 길이다. 어긋나면 `400`과 `INVALID_INPUT`이고 `fields`에 어긋난 것을 모두 `field` 이름 순으로 담는다. 세 질문이 겹치면 `field`는 `answers`다.
3. `interestIds`가 모두 지우지 않은 세부 관심사인지 본다. 아니면 `404`와 `INTEREST_NOT_FOUND`.
4. `answers[].introQuestionId`가 모두 있는 질문인지 본다. 아니면 `404`와 `INTRO_QUESTION_NOT_FOUND`.
5. 닉네임 확인과 같은 방법으로 `nickname`을 이 계정 몫으로 맡는다. 다른 계정이 맡아 둔 시간이 남아 있으면 `409`와 `NICKNAME_DUPLICATED`. 이 계정이 맡아 두었거나 아무도 맡아 두지 않았으면 맡은 뒤 넘어간다. 그 뒤 다른 사람이 이미 쓰고 있는지 DB에서 보고, 쓰고 있으면 `409`와 `NICKNAME_DUPLICATED`. 저장이 끝날 때까지 맡아 두므로, 저장하는 사이 다른 계정이 같은 닉네임을 확인해 성공하는 일이 없다. 이 계정이 맡아 둔 5분이 지났어도 그 사이 같은 닉네임을 쓰기 시작한 사람이 없으면 그대로 저장한다.
6. 아래 표의 값을 한 트랜잭션으로 저장한다.
7. 저장하다 닉네임이 겹치면 모두 되돌리고 `409`와 `NICKNAME_DUPLICATED`.
8. 땅굴 입구의 자리 번호는 그 들판의 가장 큰 번호 + 1이다. 같은 층에 동시에 확정하면 서버가 차례로 번호를 줘서 겹치지 않는다. 프론트엔드는 평소처럼 성공을 받는다. 열린 학기가 하나도 없는 등 입구를 만들지 못하면 모두 되돌리고 `500`과 `INTERNAL_ERROR`로 답한다. 저장된 것이 없으므로 같은 요청을 다시 보내도 된다.
9. 저장했으면 이 계정이 맡아 둔 닉네임을 임시 저장소에서 지운다.

| 요청의 값 | 저장하는 곳 |
|---|---|
| `nickname` | `user_profile.nickname` |
| `mole.head`, `mole.face`, `mole.neck`, `mole.hand` | `user_profile.mole_head`, `mole_face`, `mole_neck`, `mole_hand` |
| `interestIds`의 n번째 | `user_interest`에 한 줄. `interest_id`는 그 id, `sort_order`는 n(1부터) |
| `answers`의 n번째 | `user_answer`에 한 줄. `slot`은 n(1 ~ 3), `intro_question_id`, `answer` |
| 없음. 서버가 만든다 | `burrow`에 한 줄. `user_id`는 이 계정 |
| 없음. 서버가 만든다 | `burrow_entrance`에 한 줄. `term_id`는 이번 학기, `campus_floor_id`는 프로필의 캠퍼스-층(SSAFY 인증 때 고른 값), `slot`은 그 들판의 다음 자리 번호 |
| 없음. 서버가 만든다 | `user.onboarded_at`에 지금 시각 |

관심사 질문이 내가 고른 관심사의 대분류에 딸린 것인지는 검사하지 않는다. 프로필 사진은 받지 않는다.

### 응답 `data`

처음 저장했으면 `201`, 이미 온보딩을 마친 계정이 다시 불렀으면 `200`으로 답한다. 두 경우의 `data`는 같다.

| 이름 | 타입 | 설명 | 값이 오는 곳 |
|---|---|---|---|
| `userId` | 숫자 | 계정의 id | `user.id` |
| `nextStep` | enum | 항상 `HOME` | 계산: [다음에 갈 화면](02-auth.md#다음에-갈-화면) |
| `burrowId` | 숫자 | 만든 땅굴의 id | `burrow.id` |

닉네임, 관심사 같은 저장한 값은 다시 주지 않는다. 프론트엔드는 내 땅굴로 가서 [내 땅굴 API](README.md)로 받는다.

### 응답 예시

```json
{
  "success": true,
  "data": { "userId": 31, "nextStep": "HOME", "burrowId": 18 },
  "error": null
}
```

관심사를 2개만 보내고 두 번째 답변이 10자보다 짧을 때:

```json
{
  "success": false,
  "data": null,
  "error": {
    "code": "INVALID_INPUT",
    "message": "입력값이 올바르지 않습니다.",
    "fields": [
      { "field": "interestIds", "message": "3개 이상 10개 이하로 골라야 합니다." },
      { "field": "answers[1].answer", "message": "10자 이상 50자 이하로 써야 합니다." }
    ],
    "detail": null
  }
}
```

### 에러

| 상태 | `code` | 때 |
|---|---|---|
| `404` | `INTEREST_NOT_FOUND` | 없거나 지운 세부 관심사가 `interestIds`에 있음 |
| `404` | `INTRO_QUESTION_NOT_FOUND` | 없는 질문이 `answers`에 있음 |
| `409` | `NICKNAME_DUPLICATED` | 다른 사람이 쓰고 있거나 맡아 둔 닉네임. 맡아 둔 5분이 지난 뒤 확정할 때 생길 수 있다 |
`NICKNAME_DUPLICATED`를 받으면 프론트엔드는 다른 값은 그대로 둔 채 닉네임만 다시 받는다. 온보딩 1로 돌아갈지 그 자리에서 받을지는 화면에서 정한다.

## 명세에 없어 이 문서에서 정한 것

- **닉네임 확인 API**: 명세는 온보딩 1에서 중복 닉네임에 오류 문구를 띄운다고 했다. 확정 전에는 DB에 저장하지 않으므로 확인하는 API를 따로 둔다.
- **닉네임 맡아 두기**: 확인에 성공한 닉네임을 그 계정 몫으로 5분 동안 맡아 둔다. 확인과 확정 사이에 다른 사람이 같은 닉네임을 가져가는 일을 줄이려는 것이다. 5분이 지나도 겹치는 사람이 없으면 그대로 저장한다.
- **확정할 때 닉네임이 겹친 경우**: 맡아 둔 5분이 지난 뒤에는 다른 사람이 같은 닉네임을 쓸 수 있다. 이때는 저장하지 않고 `NICKNAME_DUPLICATED`로 답하고, 프론트엔드는 닉네임만 다시 받는다. 명세에는 이 경우의 화면이 없다.
- **확정 API 하나로 저장**: 단계마다 저장하지 않고 "관심사 확정"에서 한 번에 저장한다. DB 설계의 A4와 같다.
- **다시 부른 확정**: 이미 온보딩을 마친 계정이 다시 부르면 에러가 아니라 지금의 땅굴로 답한다. 버튼을 두 번 누르거나 응답을 받지 못해 다시 보낸 경우를 위한 것이다.
- **땅굴 입구를 만들지 못한 경우**: 자리 번호가 겹치면 서버가 번호를 다시 고른다. 그래도 만들지 못하면 아무것도 저장하지 않고 `INTERNAL_ERROR`로 답한다.
- **추천 질문**: 서버가 주지 않고 프론트엔드가 질문 목록에서 고른다. 고른 관심사가 확정 전에는 서버에 없기 때문이다.
- **관심사 질문과 내 관심사**: 고른 관심사 질문이 내 관심사의 대분류에 딸린 것인지 서버는 검사하지 않는다. 어떤 질문을 보여 줄지는 화면이 정한다.
- **두더지 아이템 코드**: 서버는 코드의 모양(영어 대문자 · 숫자 · 밑줄, 30자 이하)만 검사한다. 아이템 목록이 프론트엔드에 있기 때문이다. 프론트엔드는 모르는 코드를 "없음"으로 그린다.
- **가구, 무드, 미리보기**: API가 없다. 프론트엔드가 고른 관심사로 그린다. 땅굴 정보 카드의 캠퍼스 · 기수 · 층만 `GET /api/v1/me`에서 받는다.
- **프로필 사진**: 온보딩에서는 받지 않는다. 올리는 곳이 명세의 보류한 결정이다.

## 구현하며 정한 것

- **닉네임 규칙**(KAN-44): 앞뒤 공백을 지운 뒤 한글 · 영어 · 숫자로 1 ~ 12자, 영어 대소문자는 가리지 않는다([닉네임 규칙](#닉네임-규칙)).
- **닉네임 확인의 빈도 제한**(KAN-44): 두지 않는다. 로그인한 사람만 부르고 가볍다. 문제가 보이면 그때 더한다.
- **열린 학기가 없을 때 확정**(KAN-44): 입구를 놓을 들판이 없으므로 아무것도 저장하지 않고 `500`과 `INTERNAL_ERROR`. 2026 하반기가 마이그레이션에 들어 있어 운영에서는 생기지 않는다.
- **입구 자리 번호**(KAN-44): 그 들판의 가장 큰 번호 + 1이고 빈 자리는 다시 쓰지 않는다. 같은 층의 확정은 캠퍼스-층 행을 잠가 차례로 처리한다([DB 설계](../db/burrow.md#burrow_entrance)).
- **확정의 입력 검사 시점**(KAN-44): 이미 마친 계정은 본문을 보지 않아야 하므로, 완료 여부를 본 뒤에 입력을 검사한다.
