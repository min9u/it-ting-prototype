# 탐색 들판: 이동 중에도 배경을 선명하게 (가속 끈 PC, 2026-11-17)

- 요청: "탐색 시에 가만히 있을 때에는 배경화질이 좋지만, 이동할때에는 다시 안좋아지는 단점이 있고, 이게 더 어색해보여. 이동할때에도 화질을 유지할 수 있는 방법을 찾아봐봐. 트릭을 써서라도 이건 반드시 잡아야할 것 같아."
  - 멈춰 있을 때 선명 ↔ 움직일 때 흐림이 번갈아 나오는 게 가장 거슬림. 움직일 때도 멈춰 있을 때와 같은 선명도가 목표. 두더지(움직이는 것)는 조금 낮아도 되고 배경은 선명하게 (이전부터의 요구)
- 대상: 그래픽 가속이 꺼진 크롬(WARP = CPU 로 그림)의 탐색 들판 (`app/src/three/holeField.ts`). GPU(가속 켬)는 그대로
- 이전 실험: [rendering-experiments-3.md](rendering-experiments-3.md) (3차), [rendering-experiments-2.md](rendering-experiments-2.md) (탐색 들판 2차), 들판 구조 [explore-field-v3-9.md](explore-field-v3-9.md)

## 결론
**점프를 시작할 때 도착할 자리를 미리 구워 두고(두더지가 땅속에 들어가는 0.42초 동안), 카메라가 움직이는 0.4초는 들판을 다시 그리지 않고 "떠날 자리·도착할 자리"의 구운 1배 그림을 바닥 평면 투영(호모그래피)으로 옮겨 그린다. 도착하면 미리 구운 그림을 그대로 선명한 배경으로 바꿔 끼운다** (실험실 **M**, 기본 켬, 저사양만). 이동 내내 멈춰 있을 때와 같은 1배 그림이라 "선명 ↔ 흐림" 바뀜이 없어짐.

- 방법: 처음엔 2D 캔버스를 CSS 로 미는 방법(띠 192개)과 WebGL 셰이더로 옮기는 방법을 둘 다 만들어, 화면 합성 비용 시험 + 앱 안 측정으로 **WebGL(gl)** 을 기본으로 골랐음 (3·5번). CSS 띠 밀기는 `?slidemode=css` 로 남김
- 패널(오른쪽 카드) 열기·닫기로 화면이 옆으로 밀릴 때도 같은 장치 (새로 드러나는 옆 띠만 잠깐 3D)
- 움직이는 층(layer 1: 두더지·링·관심사 이펙트)은 굽지 않고 이동 중에도 3D 로 그림 (메인 세션 요청)
- 한계: 바닥 평면을 가정해서 **높은 물체(호박 0.47m·울타리 0.6m·사다리 1.1m)는 이동 한가운데에서 10~20px 어긋났다가** 위 그림이 바뀌는 순간(k = 0.5) 한 번 건너뜀 → k = 0.5 의 PSNR·가장자리 SSIM 은 기준보다 낮음(5-4). 대각선·먼 점프의 화면 모서리(두 그림 다 못 덮는 곳)는 3D 0.55배(약한 PC 0.33배)로 메워서 잠깐 흐림. 2코어에서 위쪽 먼 구멍 클릭 점프는 메움 때문에 17.5fps(기준 28.8) → 약한 PC 메움을 0.33배로 고침(5-3)

## 1. 지금 이동이 어떻게 그려졌나 (main `a72ad65`)
점프 한 번 = 두더지 들어가기(hop_down 0.42초, 카메라 그대로) → 카메라 이동 0.4초(ease-in-out) → 두더지 나오기(hop_up 0.5초).
- 멈춰 있을 때: 배경(layer 0)을 1배로 구워(sharpBake, 렌더 타깃 띠 굽기 + MSAA + 비동기 읽기) WebGL 캔버스 뒤 2D 캔버스에 깔고, WebGL 캔버스(0.55배, 투명)에는 두더지·링(layer 1)만
- 카메라 이동 0.4초: 선명한 2D 배경을 내리고 들판 전체를 **0.33배**(weak 0.22배) 렌더 타깃에 매 프레임 그려 늘려 붙임
- 도착 뒤: 두더지가 다 나오고(0.5초) 0.12초 조용해질 때까지 그 0.33배 그림을 그대로 쓰고, 그다음에 0.55배 배경 다시 찍기 → 1배 굽기(16스레드 약 0.17초, 2코어 약 0.55초) → 선명
- 그래서 점프마다 **흐린 시간이 16스레드 약 1.2초, 2코어 약 1.6초** (카메라 이동 0.4 + 두더지 나오기 0.5 + 조용 0.12 + 굽기). 사용자가 말한 "이동할 때 다시 안 좋아짐"이 이것

## 2. 조사
### 2-1. 카메라
- `PerspectiveCamera` 세로 FOV 32.3°, 내려다보기 45°, 거리 12m(높이 8.49m) 고정. **회전·확대(줌)·드래그 없음**
- 움직임은 두 가지뿐
  1. **점프** (방향키·WASD, 구멍 클릭, 미니맵, "내 땅굴로 돌아가기"): 목표점(카메라가 보는 바닥 점)만 떠날 구멍 → 도착 구멍으로 평행 이동(구역 camRect 안으로 제한). 구멍 간격은 가장 가까운 것 6m(중앙값 6.0, 최대 7.2), 방향키 점프는 보통 6~8.5m. 미니맵·내 땅굴로 돌아가기는 수십 m 도 감
  2. **패널 이동** (오른쪽 카드 열기·닫기, focusX 0.5 ↔ 0.403): `setViewOffset` 으로 화면을 가로로 밂(1920px 에서 약 186px), 지수 따라가기 τ 0.12초(약 0.5초)
  - 캠퍼스-층 바꾸기는 장면을 새로 만듦(카메라 이동 아님)
- 원근 카메라라 화면이 통째로 평행 이동하지는 않음: 바닥과 나란히 움직이면 **바닥 평면의 점은 호모그래피(투영 변환) 하나로** 옮겨지고, 카메라에 기울기(roll)가 없어서 **화면의 가로 행은 가로 행으로** 감. 아래 행(가까움, 깊이 9.3m)이 위 행(16.9m)보다 1.8배 많이 밀림. 앞뒤로 움직이면 행마다 가로 확대도 다름
- 1080px 화면에서 6m 좌우 점프는 화면 아래쪽이 약 1100px, 위쪽이 약 600px 밀림 → 이동 도중엔 떠날 자리 그림도 도착할 자리 그림도 화면을 다 못 덮는 곳이 생김(특히 대각선 점프의 모서리, 먼 점프)

## 3. 후보와 시험
### 3-1. 그림을 옮기는 방법: 화면 합성 비용 (`explore/gpu/move/comp-bench.*`)
가속 끈 크롬은 화면 합성도 CPU(소프트웨어 합성기, 한 스레드)가 함. 1904×985 그림을 옮기는 방법별로 rAF fps 와 합성 한 번에 드는 시간(추적 `Display::DrawAndSwap`)을 잼. 모든 경우 위에 0.55배 투명 WebGL 캔버스(링 흉내)가 있음 (지금 멈춰 있을 때와 같은 구성)

- 소프트웨어 합성기는 **한 스레드**라 16스레드·2코어가 거의 같고, 축에 맞춘 평행 이동·확대는 빠르지만 투영·기울임은 느린 길

- 띠 수(32 ↔ 64)는 합성 비용에 거의 영향 없음 (넓이가 같아서)
- 시험만 보면 16스레드 = WebGL 1배(gl), 2코어 = 띠 두 장(css)이 좋아 보였지만, **앱 안에서 재 보니 2코어도 gl 이 나았음**(5-3: css 는 띠 캔버스 384개를 만들고 처음 합성하는 비용과 합성기 두 장 비용) → gl 을 기본으로

| 이동 중 새로 드러나는 가장자리만 채우기 | 채택 (빈 곳만 3D, 0.55배) | 두 그림 다 못 덮는 곳(대각선 점프의 모서리·먼 점프)만 그 사각형 안에서 그림. 빈 곳이 화면 30% 넘으면 0.33배 |

## 4. 채택한 방법: 도착 자리 미리 굽기 + 구운 그림 옮기기 (M)
코드: `app/src/three/moveSlide.ts`(css 띠 밀기 `createSlide`, gl 옮기기 `createGlSlide`), `app/src/three/holeField.ts`("M 이동 중에도 선명" 블록).

1. **점프 시작**(방향키·클릭·미니맵): 지금 선명한 배경 그림을 칸 0 에 넣고(떠날 자리, 찍은 카메라 복제본과 함께), 도착 카메라(목표점 = 도착 구멍)로 **도착 자리를 굽기 시작**(sharpBake 를 두 번째 2D 캔버스 `nextCv` 로). 이미 구운 적이 있으면(IndexedDB 기억, 점프 시작 때 미리 읽음) 굽지 않음. 다 구우면 다음 프레임에 도착 자리 0.55배 배경(`bdNext`, 두더지 가림 깊이)을 한 번 찍고, 그다음 프레임에 칸 1 에 넣고 기억에 저장. **한 프레임에 한 가지씩**이라 두더지가 들어가는 동작은 계속 그려짐
2. **두더지가 다 들어갔는데(0.42초) 아직이면 땅속에서 기다림**(`dig`, 최대 0.9초). 노란 목표 링은 계속 깜빡임. 16스레드는 준비가 0.15~0.2초라 기다리지 않음
3. **카메라 이동 0.4초**: 들판(layer 0)을 다시 그리지 않고 구운 두 그림을 옮김. 앞 절반(k < 0.5)은 떠날 자리, 뒤 절반은 도착 자리 그림이 위. 처음(k = 0)·끝(k = 1)에서 위 그림은 원래 그림 그대로
   - **gl (기본)**: WebGL 캔버스를 1배로 키우고(이동하는 동안만) 두 그림을 텍스처로(점프 시작·준비 끝에 미리 올림), 화면 네 모서리 → 바닥 평면(높이 0.06m) → 찍은 카메라 화면으로 호모그래피를 풀어 셰이더에서 옮김
   - css (`?slidemode=css`, 시험용으로 남김): 그림을 가로 띠 192개(각 약 5행)로 잘라 띠마다 CSS `translate3d + scale` → 화면 합성기가 옮김. 띠 가운데 행의 양 끝으로 가로 위치·배율, 가운데 열의 위·아래로 세로 위치·배율(띠 끝 오차 ±0.65px). 합성기가 띠 위아래 끝 한 줄을 반투명하게 그려서 띠를 아래로 3행 겹침
   - 두 그림 다 못 덮는 곳은 32px 격자로 찾아 사분면마다 경계 상자 → 그 사각형만 3D 로 렌더 타깃에 그려 붙임 (css 는 띠가 덮은 곳을 다시 투명하게 뚫음)
   - 움직이는 층(layer 1: 노란 링·관심사 이펙트, 두더지는 이때 땅속)은 그 위에 **3D 로 계속** 그림
4. **도착(k = 1)**: 미리 구운 그림 캔버스와 지금 캔버스의 역할을 바꾸고(`nextCv` ↔ `sharpCv`), 깊이도 바꿈(`bdNext` ↔ `backdrop`), gl 이면 캔버스를 0.55배로 되돌림 → **그 프레임부터 멈춰 있을 때와 똑같은 그리기**(선명한 2D 배경 + 두더지 0.55배). 예전의 "도착 뒤 0.33배 → 조용해지면 다시 굽기"가 없음
5. **패널 이동**(오른쪽 카드 열기·닫기, focusX): 같은 장치. 지금 그림을 칸 0 에, 새 구도를 미리 구워 칸 1 에. 새로 드러나는 옆 띠(약 186px)만 그동안 3D 로 메움. 다 되면 바꿔 끼움
6. 미리 못 구운 경우(들어오자마자 첫 굽기 전에 점프, 굽기 실패, 점프 중 패널 이동)는 **예전 길**(이동 중 0.33배). 그래도 도착 그림이 준비되면 그때 바꿔 끼움
7. GPU(가속 켬)는 굽기(S)가 없어서 이 장치도 없음 → 그림·fps 그대로

- 왜 정확한가: 카메라가 바닥과 나란히만 움직여서 바닥 평면은 호모그래피로 정확히 옮겨짐. 바닥보다 높은 것(호박 0.47m·울타리 0.6m·사다리 1.1m)은 평면 가정 때문에 **이동 도중에만** 조금 어긋남(6m 점프 가운데에서 호박 약 10~20px). 처음·끝은 정확한 그림이라 멈춰 있을 때와 같고, 가운데에서 위 그림이 바뀔 때 높은 물체가 그만큼 한 번 건너뜀 (0.4초 이동의 가장 빠른 순간, 화면이 한 프레임에 수십 px 움직일 때)
- 왜 빠른가: gl 은 셰이더 한 번(텍스처 두 장 읽기) + 링, css 는 메인 스레드가 띠 384개의 transform 만 바꾸고 합성기가 옮김. 둘 다 들판 전체 다시 그리기(PBR·환경맵)가 없음
- 처음엔 기기 단계로 나눠(strong → gl, weak → css) 만들었다가 2코어 측정(5-3) 뒤 gl 하나로. 약한 PC 는 빈 곳 메우기만 늘 0.33배. 시험용 `?slidemode=gl|css`

### 5-1. 측정 조건
- 이 PC(i7-11700, 16스레드) 크롬 157 헤드리스 1920×1080, 새 프로필 + 가속 끔 → WARP. "2코어" = 크롬을 CPU 2개에 묶음. 공유 빌드(`build:share` → `vite preview`)

- 16스레드 묶음은 "구운 그림 메모리 기억"을 넣기 전 빌드, 2코어 묶음은 "약한 PC 빈 곳 0.33배"를 넣기 전 빌드로 잼 (마지막 커밋과 다른 점은 이 둘뿐, 5-4)

## 7. 바꾼 파일 (holeField 구조 변경 포함 — 관심사 이펙트 작업과 합칠 때 볼 곳)
- 새로: `app/src/three/moveSlide.ts` — `createSlide`(css 띠 밀기: 가로 띠 192개 2D 캔버스 × 칸 2, 빈 곳 찾기 `gaps`, 띠 자리 투명하게 `punch`, `prebuild`) · `createGlSlide`(gl 옮기기: 텍스처 2장 + 호모그래피 셰이더, `solveHomography`)
- `app/src/three/holeField.ts`
  - 머리 설명에 M 한 줄, 상수 `HOLD_MAX`(0.9초)·`FILL_LOW_FRAC`(0.3)
  - `anim.phase` 에 **`dig`**(두더지가 들어간 뒤 도착 그림을 기다림) 추가, `anim.slide`·`anim.k`. `stepAnim`: down → (dig) → cam → up, cam 시작 때 `beginCam()`, k = 1 에서 준비됐으면 `finishPrep()`
  - `jump()`: 떠날 자리 그림을 칸 0 에 + `startPrep(도착 카메라, 자리 키)`
  - 새 블록 **"M 이동 중에도 선명"**(S 블록 바로 아래): `slide`·`glSlide`·`nextCv`(두 번째 선명한 2D 캔버스)·`bdNext`·`prep` 상태와 `prepStep`·`finishPrep`·`drawSlide`·`drawSlideGl`·`enterGl/exitGl`(이동 중 캔버스 1배)·`focusTr`(패널 이동)
  - `frame()`: 그리기 전에 `prepStep()`/`finishPrep()`, 패널 이동 시작·취소, 그리기 분기 `drawSlide`(점프·패널) → `drawMoving`(예전 길) → `drawStatic`
  - `sharpOff()` 는 prep 이 굽기를 쓰는 중이면 굽기를 취소하지 않음, `stepSharp()` 는 prep 중엔 쉼, 굽기 결과는 늘 `makeSharpCv()` 캔버스로(`baker.start(..., into)`), `seatKey(seat, focus)`
  - `busy` 에 `prep`, `resize` 에 `exitGl`·`cancelPrep`·띠 크기, `dispose` 에 새 자원, 예열 끝에 두 셰이더 컴파일 걸기, 기기 단계가 바뀌면 `tierNow`
  - **이펙트 작업이 지킬 것**: layer 1 에 그리면 이동 중에도 `drawSlide*` 의 "움직이는 층" 렌더에서 3D 로 그려짐(굽지 않음). 멈춰 있을 때의 부분 다시 그리기(P, `dynRect`)는 두더지·링 둘레만 다시 그리므로, 늘 움직이는 이펙트는 `dynRect` 에 그 범위를 더하거나 `fullNext` 를 켜야 함 (이번 작업과 무관하게 원래 그럼)
- `app/src/three/sharpBake.ts`: `start(..., into?)` — 이번 결과를 넣을 캔버스 (도착 자리를 지금 그림을 둔 채 따로 굽기)
- `app/src/three/staticBackdrop.ts`: `capture(scene, camera, mask?, rects?)` — 사각형들에만 그리기 (빈 곳 메우기)
- `app/src/lib/lowLab.ts`·`components/LowLab.tsx`: 실험실 **M 이동 중에도 선명** (기본 켬)
- 측정: `explore/gpu/move/`(comp-bench.html·.mjs 합성 비용, move-shots.mjs·move-quality.mjs·.py 이동 도중 화질, move-summary.mjs 성능 표), `explore/gpu/cdp-scene.mjs`(`TRACE=1` 화면 합성 프레임), `explore/gpu/round3-perf.mjs`(`move16`·`move2` 묶음, `PERF_OUT`). 결과 `explore/gpu/results/move.json`, 그림 `explore/gpu/results/move/`

## 8. 실제 브라우저로 볼 것 (가속 끈 크롬: `chrome://settings/system` 에서 "그래픽 가속 사용" 끄고 다시 시작)
- 띄우기: `cd app && npm run build:share && npx vite preview --outDir dist-share --port 5351` → `http://localhost:5351/#/burrow/explore` (또는 `npm run dev`)
- **방향키로 옆 구멍 점프**: 두더지가 들어가고 → 카메라가 미끄러지는 0.4초 동안 들판(길·잔디·작물)이 **멈춰 있을 때처럼 선명한지**, 도착해서 두더지가 튀어 오를 때 **선명 ↔ 흐림 바뀜이 없는지**. 이동 가운데쯤 호박·울타리·사다리 같은 높은 물체가 살짝 "툭" 건너뛰어 보이는지(평면 가정의 한계, 거슬리는지 알려 주세요)
- **대각선·위아래 점프, 구멍 클릭, 미니맵으로 먼 곳**: 화면 모서리에 잠깐 흐린 곳(빈 곳을 3D 로 메운 곳)이 거슬리지 않는지. 먼 곳은 가운데쯤 흐린 부분이 넓어짐
- **오른쪽 카드 접기·펴기**: 화면이 옆으로 밀릴 때 흐려지지 않는지 (새로 드러나는 옆 띠만 잠깐 흐림)
- **약한 PC 흉내** `?tier=weak` (또는 🧪 → 단계 "약한 PC"): 처음 가는 구멍이면 두더지가 땅속에서 조금 더 머물 수 있음(이번 측정 0~0.05초), 그래도 이동이 선명한지. 대각선 점프 모서리의 메움은 더 흐림(0.33배)
- 비교: `?fslide=0` 또는 🧪 **M** 끄기 = 예전(이동 중 흐림), `?slidemode=gl|css` 로 방법 고정
- GPU PC 는 바뀐 것 없음 (확인만)

## 9. 남은 것
- **높은 물체 시차**: 평면 가정이라 이동 가운데에서 호박·울타리·사다리가 10~40px 어긋났다가 위 그림이 바뀔 때 한 번 건너뜀. gl 경로에 깊이 격자 재투영(구울 때 깊이도 저장해 정점마다 옮기기)을 얹으면 없앨 수 있음
- **2코어급 땅속 기다림**: 도착 자리 굽기(0.5~0.6초)가 두더지 들어가기(0.42초)보다 길어 0.2~0.4초 더 기다림. 쉬는 동안 다음에 갈 가능성이 큰 이웃 한 곳(같은 방향)만 미리 굽기, 또는 깊이(bdNext)를 깊이만 그리는 재질로 싸게 하기
- 먼 점프(미니맵·내 땅굴로 돌아가기)는 이동 가운데 두 그림 다 못 덮는 곳이 넓어 그 부분은 흐림(0.33배)
- 실제 SSAFY PC·실제 아티팩트(인터넷)에서는 안 잼. 측정 때 다른 작업자가 빌드·크롬을 돌려 CPU 가 20~70% 오르내렸음 (25% 아래가 될 때까지 기다렸다가 잼)
