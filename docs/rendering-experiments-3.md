## 2. 한 것 (후보)
### 2-1. 기기 자동 맞춤 (`lib/deviceTier.ts`, `engine.ts` Quality.tier)
- 단계 셋: **gpu**(가속 켬, 원래 품질) · **strong**(가속 꺼짐, CPU 넉넉 = 이 PC 16스레드) · **weak**(가속 꺼짐, CPU 약함 = 2코어 흉내)
- gpu / 저사양은 지금처럼 감지(`graphicsTier`, 렌더러 문자열·`failIfMajorPerformanceCaveat`)로 정함. **GPU 로 감지됐는데 처음 2초 평균 프레임이 50ms 를 넘어 저사양으로 내린 적이 있으면 3일 동안 기억**해서 다음 방문은 처음부터 저사양 (예전엔 그 탭에서만)
- 저사양 안의 strong / weak 는 **실제 그리기 시간**: 장면이 다 차려진 뒤 배경 한 번 그리기(A, `staticBackdrop.capture`)를 걸고 GPU 펜스가 풀릴 때까지를 재서(메인 스레드는 기다리지 않음, `engine.ts timeGpuWork`) 메가픽셀당 ms 로 바꿈. 이 탭에서 5번까지 재서, 3개부터 **가장 작은 값 > 50 이고 첫 값(텍스처 올리기가 끼어 늘 큼)을 뺀 나머지 중 두 번째로 작은 값 > 110**(메가픽셀당 ms)일 때만 weak
  - 처음(11-16)엔 "가장 작은 값 > 110" 이었는데, 측정해 보니 땅굴은 2코어에서도 가끔 빠른 값(60~78)이 나와 판정이 strong ↔ weak 를 오갔음. 이번 측정 88번의 값으로 규칙을 골랐음 (아래 4-1). strong 을 weak 로 잘못 보면 화질(MSAA)이 내려가므로 애매하면 strong 쪽
  - 옛 밭(랜딩)은 장면이 무거워 들쭉날쭉해서 재지 않음
- 결과는 `localStorage digul.tier.v1`(try/catch) → **다음 화면·다음 방문부터** 처음부터 그 단계. **탐색 들판은 그 자리에서도 바꿈**(`onLowTierChange`: 굽기가 쉬고 있을 때 굽기 띠·MSAA, 다음 카메라 이동부터 해상도). 기억이 없는 첫 방문은 strong, 단 **논리 프로세서 4개 이하 PC 는 weak 로 시작**(`navigator.hardwareConcurrency`. 이번 2코어 흉내(크롬을 CPU 2개에 묶기)로는 시험하지 못함)

### 2-2. 예열 다시 짜기 (`three/warm.ts warmScene`) — 남은 것 (c)(d)
- 2차 예열: 장면 전체를 `compileAsync` 로 컴파일(배경 렌더 타깃용·캔버스용 두 번) + 텍스처 + 물체마다 1×1 그리기를 25ms 씩 묶어서
- 문제 (CPU 프로필·GL 호출 시간 재기): WARP 에서 프로그램을 처음 쓸 때 three 가 부르는 동기 호출(`getProgramInfoLog` 등)이 **GPU 프로세스가 그 프로그램 링크와 앞서 건 일을 끝낼 때까지** 기다림 (하나에 0.1~0.3초). 25ms 묶음이면 다음 묶음의 동기 호출이 앞 묶음의 링크를 기다려서 멈춤이 남음. 또 배경 층(layer 0)·움직이는 층(layer 1)을 두 군데 다 예열해서 쓰지 않는 셰이더 조합까지 링크
- 3차 (11-16): ① 층마다 **실제로 그려지는 곳만** 컴파일·그리기(layer 0 → 배경 렌더 타깃, layer 1 → 캔버스, 카메라 층도 실제와 같게) ② 같은 재질·정점 형식·그리는 곳이면 하나만 ③ 1×1 그리기 하나마다 GPU 펜스로 끝날 때까지 비동기로 기다림(`waitGpu`, 4ms 마다 확인) ④ 텍스처도 한 장씩 올리고 기다림 ⑤ 선명한 배경 굽기용 렌더 타깃·톤매핑 셰이더도 작은 크기로 한 번
- **11-17 고침** (측정에서 드러남, 아래 표의 "11-16" 열): 멈춤은 줄었지만 **다 보이기까지가 길어짐** — 남의 땅굴 2.46 → 3.15초, 온보딩 미리보기 2.57 → 3.05초, **탐색 들판 바꾸기 0.40 → 1.65초**. `window.__warmSteps` 로 나눠 재 보니 들판 바꾸기 예열 1.1초 중 **컴파일 0.95초**, 그리기는 0.06초. 물체마다 `compileAsync` 를 불러 10ms 확인 루프가 54개 따로 돌고, 그 확인(`COMPLETION_STATUS` 동기 호출)이 셰이더를 링크하는 GPU 프로세스를 계속 붙잡았음
  - 그려지는 곳마다 `renderer.compile`(컴파일만 걸어 둠)을 다 부르고 **렌더러 프로그램 전부를 루프 하나로**(16ms 마다) 기다림 (`programsReady`) → 컴파일 0.95 → **0.09초**
  - 1×1 그리기는 셰이더가 다 링크된 뒤라 메인 스레드 **8ms 씩 묶어서** 펜스 한 번 (54개 → 펜스 4~5번)
  - 들판 바꾸기 1.70 → **0.56초** (같은 조건 시험, 돌아오기 0.29초). 시험 손잡이 `?wone=0`(물체마다 compileAsync) `?wbatch=0`(하나마다 펜스)
  - 텍스처 올리기도 8ms 묶음으로 해 봤지만(가속 끈 남의 땅굴 20장에서 0.1초 안팎 이득, 흔들림 안쪽) GPU 탐색 들판에서 텍스처 2장 기다리기가 0.06 → 0.29초로 늘어 되돌림 (한 장마다 기다림)
- 적용: 땅굴 방(`?rwarm=0` 예전), 탐색 들판(`?hwarm=0` 예전), 찻방 두더지(새로, `?compile=0` 끔), **랜딩·둘러보기 옛 밭(새로, `?compile=0` 끔)**: 예전엔 마운트하자마자 첫 프레임에서 셰이더를 컴파일해 첫 화면이 멈췄음 → 밭을 다 만든 뒤 예열이 끝날 때까지 캔버스를 투명하게 두고(그동안 같은 구도의 정지 그림) 끝나면 0.35초에 걸쳐 나타남. 나중에 불러오는 두더지·굴은 따로 예열하고 나서 보이게
- 랜딩 밭·찻방 두더지는 GPU 에서도 3차 예열 (GPU 첫 멈춤 819 → 355ms, 178 → 60ms). 땅굴·탐색 들판은 GPU 에서 2차 예열 그대로 (3차 방식은 WARP 의 동기 호출 멈춤용이라 GPU 에선 이득이 없었음, 6번)

### 2-3. 선명한 배경 굽기 (`three/sharpBake.ts`) — 남은 것 (a)
- 2차 S: 배경(layer 0)을 캔버스 크기를 1배로 키워 한 번에 그리고 읽음(탐색 들판은 PBO 비동기, 땅굴은 그 자리에서 1.5배 슈퍼샘플을 `drawImage`). 2코어에선 한 장(0.3~0.5초) 동안 두더지가 통째로 밀림
- 3차: **렌더 타깃에 띠로 나눠 여러 프레임에 굽고**(scissor, 한 프레임에 띠 하나) → 다 되면 톤매핑·sRGB 를 한 번에 → **PBO + 펜스로 비동기로 읽어** 뒤 2D 캔버스에. 캔버스 크기를 바꾸지 않아서 굽는 동안에도 두더지 층은 그대로 그림. 안티앨리어싱은 1.5배 슈퍼샘플(픽셀 2.2배) 대신 **MSAA 4×** (GPU 화면과 같은 방식)

## 7. WebGL 이 없을 때 (`--disable-3d-apis`)
- 내 땅굴·남의 땅굴: 3D 경계 → 로딩을 거두고 **4:3 구도 상자 그대로 고해상도 정지 그림**(2048px). 예전엔 636px 자리표시가 늘어나 흐렸음
- 탐색 들판: 경계 fallback = 들판 정지 그림(1920px). 처음엔 그 위에 "들판으로 나가는 중…" 어두운 막이 계속 남아 있어서 고침(경계 onError → 막 걷기)
- 랜딩: 밭 정지 그림이 늘 3D 아래에 깔려 있어서 그대로 보임
- 찻방: 원래대로 2D 두더지 (채팅 화면은 다른 작업 영역이라 건드리지 않음. 투명 배경 두더지 그림 `tea-duo`·`tea-group` 은 넣어 둠)
- 확인 그림: 이 문서 작업 중 헤드리스로 찍음 (`explore/gpu/results/round3/img/nogl-*.webp`)

| 정지 그림을 내 땅굴·온보딩 로딩 그림으로 | 안 함 | 관심사·가구가 사람마다 달라 다른 방이 잠깐 보였다 바뀜 → 랜딩 방(같은 방)만. 대신 두 번째 방문부터는 IndexedDB 그림 |
| 탐색 들판 로딩 그림 (빌드 정지 그림) | 안 함 | 서는 자리·층마다 구도가 달라서. 실패 대체 그림으로만 |
| FXAA 같은 싼 후처리 | 안 함 | MSAA 굽기(sRGB)로 배경 가장자리 SSIM 0.998 → 더 할 것이 없음 |
| 두더지 둘레만 1배로 따로 그리기 | 안 함 | "두더지는 조금 낮춰도 됨", 두더지 SSIM 0.97~0.98. 2코어 비용 대비 이득이 작음 |

## 실제 브라우저로 확인할 것 (가속 끈 크롬, `chrome://settings/system` 에서 "그래픽 가속 사용" 끄고 다시 시작)
- 띄우기: `cd app && npm run build:share && npx vite preview --outDir dist-share --port 5341` → `http://localhost:5341/#/...` (또는 `npm run dev`)
- **랜딩 `#/start`**: 처음에 정지 그림 → 0.4초쯤 뒤 3D 가 겹쳐 나타날 때 두더지·풀이 "툭" 바뀌어 보이지 않는지 (정지 그림은 GPU 고화질, 3D 는 0.55배라 조금 흐려짐). 첫 화면에서 바로 스크롤해도 멈칫하지 않는지
- **내 땅굴 `#/burrow`** · **남의 땅굴 `#/burrow/yerin`**: 들어온 뒤 0.2~0.7초 사이에 방이 선명해지는 순간(두더지는 그대로 움직임). **새로고침하면** 로딩 애니메이션 없이 바로 선명한 방이 보이고 3D 로 이어지는지 (IndexedDB). 가구 칠하기(`#/lab/style`)·가구 바꾸기를 하면 예전 그림이 남지 않고 다시 선명해지는지
- **탐색 `#/burrow/explore`**: 점프할 때 카메라 이동(잠깐 흐림) → 도착 → 배경이 선명해지는 순간이 거슬리지 않는지, 한 번 갔던 구멍으로 돌아오면 바로 선명한지. **캠퍼스-층 바꾸기**가 예전처럼 빨리(0.5초쯤) 되는지
- **약한 PC 흉내**: 주소 끝에 `?tier=weak` (또는 🧪 실험실 → 단계 "약한 PC"). 탐색 카메라 이동이 더 흐리지만(0.22배) 덜 끊기는지, 선명한 배경이 여러 프레임에 나눠 생기는지. 원래대로는 `?tier=strong`
- 비교 손잡이: `?stillcache=0`(구운 그림 기억 끔) · `?rbake=0`(땅굴 예전 선명한 방) · `?fstrips=1&fmsaa=0`(탐색 한 장 굽기) · `?compile=0`(예열 끔, 랜딩·찻방) · `?wone=0`·`?wbatch=0`(11-16 예열) · 🧪 "기억 지우기"
- **WebGL 이 없을 때**: 크롬을 `--disable-3d-apis` 로 띄우면(바로 가기 대상 끝에 붙임) 땅굴·탐색·랜딩이 흐린 자리표시 대신 고해상도 정지 그림으로 보이는지
- **GPU PC**: 그림·움직임이 예전과 같은지 (저사양 기능은 꺼져 있음. 예열은 GPU 에서도 돎 → 랜딩은 정지 그림 → 3D 페이드 인)

## 남은 것
- **2코어 땅굴 첫 진입 0.9~1.1초 멈춤** (기준도 같음): 그래픽이 아니라 모델 불러오기 쪽으로 봄 — 공유 빌드는 Draco 해독기가 메인 스레드 JS(아티팩트에 wasm 을 못 올려서, [rendering-experiments.md](rendering-experiments.md)). 두 번째 방문은 0.32초. 다음: 공유 빌드에서도 해독을 Worker 로(1차의 D 시험판은 공유 빌드에서 빈 화면이라 껐음)
- (a) 2코어 탐색 점프 끊김 0.21~0.29초, (b) 카메라 이동 20fps: 2코어에선 메인 스레드와 WARP 가 CPU 2개를 나눠 써서, 점프 0.4초 동안 들판 전체를 그리는 일 자체가 무거움. 다음 후보는 2차에서 보류한 "이동 전·후 그림을 땅에 투영해 늘려 보이기(재투영)" 또는 weak 에서 카메라 이동을 아예 잘라 붙이기(이동 없이 페이드)
- 첫 방문 2코어는 판정 전까지 strong 으로 시작 (탐색 들판만 그 자리에서 바꿈). `hardwareConcurrency ≤ 4` 짐작은 이번 흉내로 시험하지 못함 → 실제 약한 PC 에서 `digul.tier.v1` 값과 함께 확인
- 2코어 탐색 첫 방문이 0.4초 늦게 보임 (sRGB 굽기용 예열). 예열을 "보이기 전 꼭 필요한 것"과 "첫 굽기 전까지만 되면 되는 것"으로 나눠 뒤엣것을 보이고 나서 하면 줄일 수 있음
- 찻방 2코어는 두더지가 예열 뒤에 나타나 0.5초 늦음 (그동안 2D 두더지)
- 랜딩·찻방 화질은 GPU 와 차이가 큼(후처리 없음, 이번 범위 밖)
- 실제 아티팩트(인터넷)·다른 SSAFY PC 에서는 안 잼. 2코어 값은 흔들림이 커서(±150ms) 2번 중앙값으로는 작은 차이를 가리기 어려움
