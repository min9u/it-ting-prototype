## 기획 규칙 (2026-11-21, 기획 담당 결정)

1. 대분류 큰 가구는 관심사로 **자동 고정**한다(사용자가 고르지 않음).
2. 세부 관심사 소품:
   - 이름에 `/` 로 여러 개가 묶인 세부 관심사(예: `헬스/필라테스/요가` → 아령 · 매트 · 바렐)는 **묶음 안의 단어 중 하나를 고른다**.
   - 한 단어 세부 관심사(예: `강아지`)는 **소품이 고정**이라 고를 수 없다.
3. 꾸미기 탭 이름은 "소품 · 두더지"(+ 개발 실험 "색" 탭 유지)로 바꾼다.

## 보류: 소품 탭은 3D 핸드오프 v3.8 적용 뒤에 만든다

- 처음에 현재 앱 카탈로그만으로 소품 탭을 만들려 했으나, **`/` 관심사 58개 중 17개는 소품이 없고 14개는 1개뿐**이라 고를 수 있는 건 21개(억지 포함 27개)였다. 소품이 없어 멈추고 보고했다.
- 이후 **3D 관심사 소품 v3.8 핸드오프**가 도착했다: `/` 로 나눈 단어마다 모델이 1개씩, **총 164개**. 대분류 큰 가구의 자동 배치도 v3.8에서 없어진다. 소품 부족 문제가 해결되고 가구 배치 규칙도 바뀌므로, 이 핸드오프는 **별도 브랜치로 먼저 들어온다**.
- 그래서 F4에서는 소품 탭을 만들지 않는다. **v3.8 적용 뒤에 소품 탭을 Figma 가구 탭(`711:7994`) 모양으로 만들 예정**이다. 그때 쓸 내용:
  - 모양: 패널 크기, 칩, 제목 줄("pill + tag + 패널 제목"), 후보 카드 크기·간격·✓ 선택 테두리, 하단 취소/저장하기는 Figma `711:7994` 그대로.
  - 칩: 내가 고른 세부 관심사 중 `/` 로 묶인 것만(한 단어 관심사는 칩에 안 나옴).
  - 제목: `헬스/필라테스/요가 소품 고르기 · 3개 중 1개`.
  - 후보 카드: 그 관심사의 단어마다 소품 1개(썸네일 + 이름). 처음 값은 지금 자동으로 놓이는 소품. 고르면 방에 바로 보이고 "저장하기"로 저장.
- 지금 앱의 가구 탭(`DecorPanel.tsx` 의 `FurnitureTab`, `data/myBurrow.ts` 의 `furnitureCandidates`)은 세부 관심사 칩 + 선반 소품 후보 3개 구조다. Figma(대분류 11칩, 대분류 가구 후보)와 다르지만 **v3.8 때 통째로 바뀌므로 이번엔 손대지 않았다**.

### DB (`docs/db/account.md`, `docs/db/burrow.md`)
- `account.md` 197행("어느 관심사에 어느 가구인지는 프론트엔드가 갖는다"), 211행("가구는 … 사용자가 고르지 않으므로 저장하지 않는다")이 **소품 선택에서는 틀린다**. 선택을 저장할 칸이 필요하다.
- 제안: `user_interest` 에 `prop_choice` (VARCHAR, 소품 코드, NULL 이면 기본 소품) 칸을 추가하거나, 별도 테이블 `user_interest_prop (user_id, interest_id, prop_code)` (PK `user_id, interest_id`). 소품 코드는 `data/interestTags.ts` 의 영어 id 처럼 영어 소문자 enum(표: `docs/backend/interest-enum.md` 에 소품 코드 표를 추가). 관심사를 뺄 때 같이 지운다(ON DELETE CASCADE).
- `burrow.md` 158행("방 안의 모습(가구 …)은 저장하지 않는다. 주인의 관심사로 그린다")도 "소품은 주인이 고른 값으로 그린다"로 수정.
- 길이·제약: 한 사용자의 관심사 최대 10개이므로 소품 선택 행도 최대 10개.

### API (`docs/api/04-my-burrow.md`)
- 26행·42행("가구와 땅굴 무드는 저장하지도 주지도 않는다") → `GET /api/v1/me/burrow` 응답의 `interests[]` 각 항목에 **`propCode`(고른 소품, 없으면 null)** 를 담는다.
