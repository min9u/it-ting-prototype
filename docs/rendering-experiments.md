# 렌더링 개선 실험 (실제 SSAFY PC, 2026-11-13)

- 요청: "지금 싸피 컴퓨터에 연결된 상태니까 개선방법들을 우선순위대로 실험해봐" ([rendering-overview.md](rendering-overview.md) 3번의 순서)
- 이 PC: i7-11700 (8코어 16스레드), RTX 5060 Ti가 있지만 **크롬 설정에서 그래픽 가속이 꺼져 있음**(정책 아님, 사용자 설정) → 크롬 157이 WARP(`Microsoft Basic Render Driver`, CPU)로 그림. 즉 지금까지 흉내 내던 "SSAFY PC 조건" 그대로. 코어 제한(AFF) 없이 잼
- 대상: 공유 빌드(`npm run build:share`, 아티팩트에 올리는 것)를 `vite preview`로 띄워서 잼

## 측정 방법
- `explore/gpu/cdp-load.mjs` (새로 만듦): 새 프로필(캐시 없음)로 `#/burrow`를 열고 "땅굴 파는 중" 로더가 사라질 때까지
  - `readyMs` 다 차려진 방이 보이기까지, `longTaskMs` 그동안 50ms 넘게 메인 스레드를 막은 작업 합, `longTaskMax`·`worstFreezeMs` 가장 긴 멈춤(이 동안 로딩 애니메이션·버튼이 멈춤)
  - cold = 첫 방문, warm = 새로고침(HTTP 캐시 있음). 3번 재서 중앙값. `MEASURE_TO`로 땅굴 → 탐색하기 → 땅굴 전환도 잼
  - `PROFILE=1`이면 CPU 프로필을 남기고 `explore/gpu/profile-top.mjs`로 함수별·가장 긴 구간 요약
- `explore/gpu/cdp-move.mjs` (원래 있던 것): 쉬기 → 걷기 → 쉬기 구간의 페이지 rAF fps·장면 fps·긴 작업
- `explore/gpu/cdp-eval.mjs`: 가속 끈 크롬에서 기능 지원 확인
- 결과 JSON: `explore/gpu/results/load/`

## 2. 처음 들어올 때 멈춤 줄이기

| 변경 | 첫 방문 ready / 긴 작업 / 가장 긴 멈춤 | 새로고침 ready / 가장 긴 멈춤 |
|---|---|---|
| 기준 | 2369 / 1876 / 717ms | 1732 / 467ms |
| ① base64를 `Uint8Array.fromBase64`로 (크롬 140+) | 2077 / 1601 / 717 | 1534 / 517 |
| ② + Draco 해독을 Worker로 | 2031 / 1035 / 700 | 1546 / 400 |
| ③ + `compileAsync`만 (실패) | 1938 / 1367 / 583 | 1692 / 583 |
| ④ + 예열 (셰이더 미리 컴파일 + 텍스처 나눠 올리기 + 그리기 예열, 그동안 루프 쉼) | **2217 / 418 / 150** | 1899 / 133 |

- ① `glb.ts bytesOf`: 브라우저 내장 base64 해독. 없으면 예전 방식. **기본**
- ② `dracoMain.ts` + `dracoWorker.ts` + `dracoCore.ts`: 공유 빌드에서 Draco를 module Worker에서 풂. Worker를 못 만들거나 실패하면 메인 스레드(해독기는 그때만 불러옴). 메인 스레드 힙도 86 → 68MB. **기본** (`?dracow=0`으로 끔)
- ③ 처음엔 효과가 없었던 이유 두 가지 (CPU 프로필로 찾음)
  1. 저사양의 방은 배경용 렌더 타깃(선형 HalfFloat)에 먼저 그려져서 캔버스와 셰이더 종류가 다름 → 두 군데 다 컴파일 (`staticBackdrop.precompile`)
  2. 렌더 루프가 이미 돌고 있어서, 컴파일을 기다리는 사이에 일반 프레임이 다 차려진 방을 먼저 그려 버림 → 예열 중에는 루프가 그리지 않게 (`warming`)
  - 그리고 WARP(ANGLE D3D11)는 프로그램이 이미 있어도 **물체를 처음 그릴 때** 파이프라인을 만들며 0.3초쯤 멈춤 → 메시를 몇 개씩만 보이게 해서 1×1 영역에 그리고 쉬기를 반복(25ms 단위)해 짧은 작업 여러 개로 나눔 (`roomScene warmDraws`)
- ④ 결과: **가장 긴 멈춤 0.72 → 0.15초, 긴 작업 합 1.9 → 0.4초.** 다 차려지는 시각은 0.1~0.2초 늦어짐(일을 나눠서). 로딩 애니메이션이 끊기지 않는 쪽이 낫다고 보고 **기본** (`?compile=0`으로 끔)
- GPU(이 PC의 RTX, 가속 켬)도 확인: ①② 적용으로 첫 방문 ready 2113 → 1696ms, ④까지 켜면 가장 긴 멈춤 317 → 150ms(새로고침 100 → 34ms), ready는 0.1~0.2초 늦음 → GPU에도 기본으로 켬
- 화면 확인: 예열 뒤에도 방·두더지·가구가 정상 (WARP·GPU 스크린샷)
- 탐색하기는 첫 프레임을 마운트하자마자 그려서(로더 없음) 같은 예열을 넣으려면 로더부터 필요 → 다음 단계

## 3. D 땅굴을 Worker에서 그리기 → 기본으로 하지 않음
- 공유 빌드에서 D를 켜면 **방이 아예 안 보임**(빈 화면). 오류 메시지도 없음. 오늘 바꾸기 전 커밋(28d208e)으로 빌드해도 똑같아서 원래 있던 문제
- D는 원래도 선명한 방(S)·말풍선·가구 이름표를 못 씀. 2번 이후 메인 스레드의 가장 긴 멈춤이 0.15초라 D로 얻을 것이 적음
- 결론: 시험판 그대로 둠(기본 끔). 다시 살리려면 공유 빌드에서 빈 화면이 되는 원인부터

## 4. 선명한 방 그림(S) 기억해 두기 → 기본
- S는 멈춰 있을 때 방을 고해상도로 한 번 그림. 이 PC(16스레드)에서는 긴 작업 하나 약 0.13초, **2코어로 묶으면 0.5초**(가장 긴 멈춤의 원인)
  - 2코어, 첫 방문: S 켬 가장 긴 멈춤 500ms / 끔 233ms
- 같은 탭 안에서 (방 주인·관심사·벽지·크기·카메라)가 같으면 찍어 둔 그림을 그대로 씀 (`roomScene SHARP_CACHE`, 최근 3개, `?sharpcache=0`으로 끔). 새로고침하면 사라짐
- 땅굴 → 탐색하기 → **다시 땅굴** (새로고침 뒤 3번 중앙값):

| 16스레드, 기억함 | **692ms** | **0** |

## 5. 공유 빌드에서 필요한 가구 모델만 받기 → 기본
- 원인: `import.meta.glob(..., { eager: true })`로 방 모델 14개(관심사 11 + 기본·장식·선반)를 한꺼번에 불러서, data URL이 땅굴 청크에 다 들어감. eager 쪽을 조건문으로 막아도 import가 남아서 소용없었음 → 두 빌드 모두 `eager` 없이 파일마다 따로 불러오게 바꿈 (`roomScene loadModel`). 일반 빌드에서는 파일 주소만 든 작은 청크
- 청크 크기: `roomScene` 11.7 → 3.7MB, `RoomCanvas` 8.6 → 0.57MB (원래 방 모델이 두 청크에 겹쳐 들어가 있었음). 관심사 모델은 0.3~1.2MB씩 따로
- 관심사 10개짜리 예시 방(가장 많이 받는 경우)으로 측정:

| | 받은 양(압축) | 첫 방문 ready | JS 힙 |
|---|---|---|---|
| 전 | 7.1MB | 2158ms | 71MB |
| 후 | **5.5MB** | 2175ms | **63MB** |

- 로컬 서버라 받는 시간은 거의 0이고 ready는 같음. 실제 아티팩트(인터넷)에서는 받는 양이 줄어드는 만큼 빨라지고, 관심사가 적은 방일수록 차이가 큼. 2코어에서는 청크가 나뉘어 ready가 4.8 → 5.3초로 조금 늦게 나왔음(로컬, 3번 측정, 흔들림 큼)
- 아티팩트에 올릴 파일 수가 늘어남 (glb 청크 11개). 한 번에 255개 제한 안쪽

## 6. Draco 청크 중복 → 안 함
- 공유 빌드에 해독기(약 450KB)가 세 벌: 메인 쪽 대비용(`dracoCore`), D Worker 안(`dracoCore`), Draco Worker(`dracoWorker`). Vite가 Worker마다 따로 묶어서 생김
- 사용자는 이 중 **하나만** 받음 (보통 `dracoWorker`, Worker를 못 쓸 때만 메인 쪽). 중복은 아티팩트에 올리는 용량만 늘림 → 고칠 이득이 없음

## 7. 렌더러 하나를 화면끼리 같이 쓰기 → 안 함 (추정)
- 땅굴 → 탐색하기 전환: 1.15초, 긴 작업 0.8초. 반대로 탐색하기 → 땅굴은 4번 이후 0.69초, 긴 작업 0
- 전환 비용 대부분은 밭(꽃·덤불) 만들기와 밭 셰이더 첫 그리기. 렌더러를 같이 써도 밭과 방은 재질이 달라 셰이더를 따로 만들어야 해서, 아낄 수 있는 것은 WebGL 컨텍스트 만들기(수십 ms) 정도
- 더 효과가 큰 것은 **탐색하기에도 2번 예열 적용**(로더를 보여 주며 셰이더·그리기 예열) → 다음 단계

## 추가로 알게 된 것: 이 PC는 저사양 모드가 지나치게 보수적
- `?maxfps=0`으로 10fps 제한을 풀면 땅굴·탐색하기 모두 걷는 동안 **장면 60fps, 페이지 60fps, 긴 작업 0** (A 배경 한 번 덕분)
- 즉 실제 SSAFY PC(16스레드)에서는 두더지가 10fps로 뚝뚝 움직일 필요가 없음. 2코어처럼 약한 PC에서만 10fps가 필요
- 제안: 움직이는 동안 실제 프레임 시간을 재서 여유가 있으면 15 → 30 → 60fps로 올리는 자동 조절 (코어 수 `navigator.hardwareConcurrency`는 코어 제한을 반영하지 않아 기준으로 못 씀)

## 8. fps 제한 풀기 + 팀 아티팩트 배포 (2026-11-13 오후, 사용자 결정)
